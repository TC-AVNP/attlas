Marathon session bringing the Pi homelab cluster online and deploying BFM to Kubernetes on it. Started with creating a public download page for the golden image, then spent hours physically bootstrapping three Raspberry Pi 5s — flashing NVMe, fixing locked-out SSH via EEPROM recovery and SD card swaps, setting up Cloudflare tunnels for remote access. Once all Pis were accessible, set up a Pi-only Kubernetes cluster (control plane on NVMe Pi, worker on SD Pi), deployed BFM as the first containerized service with Cloudflare tunnel ingress at bfm-dev.attlas.uk, and added a web TTY feature for SSH into slave nodes from the browser.

## Timeline

### Phase 1: Golden image download page (~16min, 12:31 – 12:47)

- Created public.attlas.uk with Caddy basic_auth (patro/patro)
- Static HTML page with design system styling + download button
- Serves bfm-universal-arm64.img.zst (1.6GB) from /var/lib/homelab-bootstrap/

### Phase 2: Cloudflare tunnel for pi-router (~15min, 12:47 – 13:02)

- Created Cloudflare tunnel "pi-router" via API
- Configured SSH routing to router.attlas.uk
- Installed cloudflared on GCP VM and pi-router
- Set up SSH ProxyCommand config for transparent access

### Phase 3: Pi cluster bootstrap (~120min, 13:02 – 17:30)

- Discovered pi-unconfigured at 10.0.0.140 via pi-router DHCP leases
- Flashed golden image to pi5-A NVMe via SSH through pi-router (1.6GB, ~3.5min)
- Expanded NVMe partition from 5.5G to 931G
- Hit SSH lockout — password auth disabled on golden image, EEPROM boot order wrong (got nibble order backwards: 0xf146 instead of 0xf461)
- Multiple SD card swap cycles between pi5-A and pi5-B to fix EEPROM and SSH
- Used pi-router's HDMI output (Pi 3 with full-size HDMI) to physically fix sshd_config
- Staged EEPROM recovery.bin on SD to change pi5-A boot order to SD-first
- Fixed NVMe cloud-init, SSH keys, and password auth from SD boot
- Both Pi5s finally booting independently — NVMe and SD card

### Phase 4: Kubernetes setup (~40min, 17:30 – 18:10)

- Initially joined Pis to GCP VM cluster — flannel broke (cross-network, can't reach cluster IPs)
- Pivoted to Pi-only cluster: pi5-basic-1 as control plane, pi5-ai-1 as worker
- kubeadm init on pi5-basic-1, flannel installed, taint removed
- Both nodes Ready with working pod networking

### Phase 5: BFM on Kubernetes (~90min, 18:10 – 01:20)

- Cross-compiled BFM for arm64 (CGO_ENABLED=0)
- Built Docker image with cloudflared included for SSH jump
- Transferred image to Pi via pi-router (two-hop SCP)
- Created Cloudflare tunnel "k8s-ingress" for bfm-dev.attlas.uk
- Deployed PV (NVMe-backed), PVC, BFM deployment, service, cloudflared deployment
- Fixed bind address (127.0.0.1 → 0.0.0.0 via BFM_BIND env)
- Fixed SSL: dev.bfm.attlas.uk → bfm-dev.attlas.uk (3rd-level subdomain not covered by Universal SSL)
- Registered brain (home-edge) and slaves (pi5-basic-1, pi5-ai-1)

### Phase 6: Web TTY + CSS fixes (~90min, 01:20 – 06:30)

- Built WebSocket-to-SSH bridge in BFM (golang.org/x/crypto/ssh + gorilla/websocket)
- SSH jumps through cloudflared to pi-router, then to slave IP
- Added xterm.js frontend with resize support
- Removed macOS browser window chrome (was mockup artifact from prototype zip)
- Fixed CSS backgrounds — .app and .main need explicit background: var(--bg)

### homelab

Three Pi 5s brought online: pi-router (existing, Cloudflare tunnel SSH), pi5-basic-1 (NVMe, 931GB), pi5-ai-1 (SD, 128GB). Major debugging around EEPROM boot order nibble ordering (LSB-first), cloud-init state corruption when SD moves between Pis, and SSH password auth disabled by incomplete cloud-init runs. Pi-only K8s cluster replaces failed cross-network GCP+Pi cluster. Flannel networking works within the LAN.

## Lessons

- Pi 5 BOOT_ORDER is LSB-first: 0xf461 means SD(1)→NVMe(6)→USB(4)→restart(f), not the reverse
- Cloud-init marks itself done per-instance; moving an SD card to different hardware can leave sshd in a broken state if cloud-init is interrupted mid-run by EEPROM recovery reboot
- Cloudflare Universal SSL only covers *.domain.tld, not *.sub.domain.tld — use single-level subdomains (bfm-dev not dev.bfm)
- Cross-network K8s (GCP + home LAN behind NAT) doesn't work for flannel/ClusterIP — kubelets connect outbound but pod networking and service DNS fail
- When a Go server runs in a container, it must bind 0.0.0.0, not 127.0.0.1 — even if Caddy proxies locally on bare metal
- Pi's SD card slot can be used as a writer when the Pi boots from NVMe — useful for flashing spare SD cards without external hardware
