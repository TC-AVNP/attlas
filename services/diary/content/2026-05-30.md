## Timeline

### Diagnosis (~3min, 16:04 – 16:07)

- Explored petboard service structure, checked Caddy configs for both path-based and subdomain routing
- Confirmed Go server was running fine (200 on localhost:7690), Caddy subdomain config existed
- Identified the real issue: HTML served assets at `/petboard/assets/...` and React Router used `basename="/petboard"` — works on `attlas.uk/petboard/` but not on `petboard.attlas.uk/` where the URL path is just `/`

### Fix (~3min, 16:07 – 16:10)

- Created `web/src/api/prefix.ts` — runtime detection via `window.location.host.startsWith("petboard.")`
- Updated `main.tsx` to use dynamic `routerBasename`
- Updated `client.ts` API_PREFIX and `events.ts` SSE URL to use shared `apiPrefix`

### Deploy and verify (~2min, 16:10 – 16:12)

- Built frontend with `npm run build`, copied dist to `/usr/local/share/petboard/dist`
- Restarted petboard service, verified assets load on both `/assets/...` and `/petboard/assets/...` paths

## Project summaries

### petboard

Fixed the blank page when accessing petboard via its subdomain (petboard.attlas.uk). The Go server already handled dual routing (path-based and subdomain) since commit 0c796bc, but the React frontend had hardcoded `/petboard` in three places: BrowserRouter basename, API prefix, and SSE events URL. Created a shared prefix.ts module that detects subdomain vs path-based at runtime.
**Lines:** L18–L144

## Lessons

- When migrating a service to a subdomain, the backend routing is only half the story — the frontend's base URL, API prefix, and any hardcoded path assumptions all need to adapt too
